# 伪装与抗封锁

**前提：没有任何协议能保证不被封。** 封锁手段一直在变，今天有效的做法明天可能失效。所以这部分设计分两半：一半是降低被识别的概率，一半是被封后尽快恢复。

## 一、降低被识别的概率

### 1. 不留"脚本指纹"

如果一个脚本的所有用户都用同样的端口、同样的伪装域名、同样的路径，这些共同点本身就成了特征。

| 项 | 做法 |
|---|---|
| 端口 | Reality 用 TCP 443，Hysteria2 用 UDP 443，与正常网站一致。443 被占时 Reality 先试其他常见的加密网页端口，都不行才随机，并提示伪装效果会下降；其余协议随机 |
| Reality 伪装域名 | 从候选中实测后随机取，不设固定默认值。候选里不收录被各种脚本当默认值用滥的域名 |
| 路径、短标识 | 全部随机 |
| 自签证书的域名 | 随机取自常见域名，不用固定值 |
| 自签证书的有效期 | 在合理范围内随机，不用所有人相同的天数 |
| 端口跳跃的范围 | 起点和宽度都随机 |
| 伪装站的内容 | 不用所有人相同的固定页面，见下文"开源会不会让特征被抓" |
| 订阅路径 | 随机长路径 |
| 以上各项的长度 | 路径、密码、短标识的长度也在范围内随机。所有人都是同样长度，本身也是特征 |

**有一类参数相反，要"和大多数人一样"。** 分享链接里的浏览器 TLS 指纹默认用最常见的 Chrome，不做随机：它的作用是混进真实浏览器的人群里，挑一个冷门的反而显眼。所以规则是：**标识类的值随机，伪装类的值从众。**

### 2. Reality 伪装目标的挑选

脚本内置一批候选域名，在本机逐个实测后筛选：

| 条件 | 原因 |
|---|---|
| 支持 TLS 1.3 和 HTTP/2 | Reality 的要求 |
| 证书有效，直接响应而非跳转 | 跳转会让伪装露出破绽 |
| 不在 CDN 后面 | 目标在 CDN 后面时，你的服务器会被当成那家 CDN 的转发点，容易被别人扫到并蹭用 |
| 从本机访问延迟低 | 握手更快，也更像"就近访问" |
| 优先与 VPS 在同一网络或同一地区 | 小机房的 IP 自称是远在别处的大厂网站，不合常理 |

检测要落到实处：确认握手**实际协商出了** HTTP/2、证书校验通过，而不只是"能用 TLS 1.3 连上"。调研中看到有脚本只做了后者。

通过筛选的候选里随机取一个。用户也可以手动指定，指定时同样做上述检查。每次体检都会复查目标是否仍然可用。

进阶做法（阶段 4）：从服务器所在的网络里找目标，伪装成"隔壁那台机器上的网站"最合常理。这需要探测邻近地址，可能被 VPS 服务商视为异常行为，所以只在用户明确开启时进行，并限制探测范围。

### 3. 应对主动探测

审查方可能直接连接你的服务器，看它如何回应。

| 模式 | 未通过认证的连接会得到 |
|---|---|
| Reality | 被原样转给真实的目标网站，探测者看到的就是那个网站 |
| 域名模式 | 回落到本机的伪装站，表现为一个普通网页 |
| NaiveProxy | 同上，协议本身即如此设计 |

域名模式的伪装站由系统自带的 Nginx 提供，仅在启用域名模式时安装。检测到机器上已有网站时不接管，改为询问。

### 4. 流量形态

| 措施 | 作用 |
|---|---|
| 分享链接默认带浏览器 TLS 指纹 | 握手特征与常见浏览器一致 |
| VLESS 默认使用 Vision 或 XHTTP | 减轻"加密连接里再套一层加密"的特征 |
| Hysteria2 默认伪装成 HTTP/3 | 看起来像普通的视频或网页流量 |
| Hysteria2 可选 Salamander 混淆 | 用于 HTTP/3 本身被针对的网络；与上一项互斥 |
| ECH | CDN 模式的进阶选项，隐藏握手中的域名 |

### 自签证书不等于跳过验证

无域名的 Hysteria2、TUIC 等使用自签证书。很多脚本的做法是让客户端"跳过证书验证"，这样任何人都能冒充你的服务器。

本项目改为**指纹固定**：把证书的指纹写进节点信息，客户端只认这一张证书。

| 客户端 | 做法 |
|---|---|
| sing-box（1.13 及以上） | 写入公钥指纹 |
| Mihomo | 写入证书指纹 |
| Shadowrocket | 写入证书指纹 |
| v2rayN | 内嵌证书本身 |
| 不支持以上任何方式的客户端 | 默认不输出该节点；用户明确要求时才生成"跳过验证"的链接，并触发[软冲突 S5](03-冲突规则.md) |

各客户端的具体字段名在写代码时对照其文档确认。

### 5. 不推荐直连使用的协议

Shadowsocks 2022、VMess 的流量是全随机字节，这本身是可被识别的特征；SOCKS5 完全不加密。它们只适合放在两台服务器之间。启用时会触发[软冲突警告](03-冲突规则.md)。

### 6. 少即是多

同时开的协议越多，对外暴露的端口越多。脚本允许全开，但会显示暴露的端口总数。日常使用建议只保留实际在用的两三种。

## 二、被封后尽快恢复

### 1. 默认就有三条路

| 线路 | 协议 | 什么时候还能用 |
|---|---|---|
| 直连 TCP | Reality | UDP 被限速时 |
| 直连 UDP | Hysteria2 | TCP 线路拥堵时 |
| 隧道 | Argo 临时隧道 | 端口被封、IP 被墙时 |

三条路同时失效的概率远低于单条。

### 2. 先判断是哪种封

见[体检与排障](07-体检与排障.md)的"四种故障"。关键区别：

- **端口被封**：只有某个端口不通，换端口就好。
- **IP 被墙**：所有端口都不通，直连类协议全部失效。

### 3. 一键迁移

| 情况 | 操作 | 结果 |
|---|---|---|
| 端口被封 | 换端口 | 新端口，新链接 |
| 怀疑伪装目标被针对 | 换伪装目标 | 重新挑选，新链接 |
| 怀疑凭据泄露 | 重置密钥 | 旧链接全部失效 |
| IP 被墙 | 切到 CDN 或 Argo | 引导绑定域名并启用套 CDN 的节点；没有域名则启用 Argo 临时隧道 |

每次迁移后都重新输出节点，并提示哪些旧链接已失效。

### 4. 其他手段

| 手段 | 作用 | 局限 |
|---|---|---|
| Hysteria2 端口跳跃 | 在一段端口间切换，缓解单端口限速 | 部分运营商按 IP 而非端口限速，此时无效 |
| 链式中转 | 入口机与落地机分离，入口被封只需换入口 | 需要两台机器 |
| 套 CDN | 外界只看到 CDN 地址，真实 IP 不暴露 | 速度取决于 CDN 线路 |
| XHTTP 上下行分离 | 上传走 CDN、下载走直连，两个方向的流量不出现在同一条连接上 | 需要域名和较新的客户端；阶段 4 提供 |

### 5. 容易混淆的一点

**WARP 不是用来过墙的。** 它解决的是"目标网站不欢迎 VPS 的 IP"，例如频繁要求验证、拒绝访问。它改变的是服务器的出口，不影响你到服务器这一段。

## 三、开源会不会让特征被抓

**结论：公开源码本身不会。所以本项目不做代码混淆。**

### 为什么不会

审查方识别的是**线路上的流量**，不是服务器上的脚本。它看不到你的 VPS 里装了什么、用哪个脚本装的；它能看到的只有经过国际出口的数据包长什么样。

而流量长什么样，是由 Xray 和 sing-box 这两个内核决定的。它们本来就是完全开源的，协议的安全性从设计上就不依赖"别人不知道原理"，而是依赖密钥。脚本只是替你把内核装好、把配置写好。

### 为什么混淆没有用，反而有害

| | 说明 |
|---|---|
| 挡不住 | 混淆的是脚本文字，流量一个字节都不会变。想研究的人装一遍抓个包就看到了 |
| 失去信任 | 用户没法确认脚本没有后门，这正是本项目要解决的问题 |
| 失去审查 | 没人能帮忙发现安全问题 |

### 真正的风险：所有人都一样

开源带来的真实风险只有一种：**脚本给每个用户生成的东西里有相同的固定值**。任何人读源码都能看到这个值，然后拿它当识别规则。调研中看到的实例：某脚本所有用户的 Reality 短标识是同一个写死的值，某脚本的自签证书域名固定为同一个大站。

防护办法不是把源码藏起来，而是**让源码里根本没有这种值**。

| 规则 | 做法 |
|---|---|
| 线路上可见的值一律每次安装随机生成 | 密钥、短标识、路径、端口、伪装域名、证书参数、跳跃范围。清单见本文第一节 |
| 源码里不出现这类常量 | 自动测试扫描源码，发现写死的凭据或标识即不通过 |
| 两次安装必须不同 | 自动测试在同一台机器上装两次，比对线路可见的参数，除 443 端口外不得相同 |
| 伪装站不用千人一面的页面 | 推荐反代到用户指定的网站或使用用户自己的页面；内置模板只作后备，有多套并随机改动细节 |
| 候选列表可替换 | Reality 伪装域名的内置候选是公开的。它们都是有大量正常访问的真实网站，被公开不构成问题；真正要避免的是域名与 VPS 所在网络不相称，见[软冲突 S4](03-冲突规则.md)。用户可以换成自己的列表 |

### 需要诚实说明的局限

- 内核自身的行为特征是所有 Xray、sing-box 用户共有的，脚本改变不了。好处是这个人群非常大。
- 审查方的具体识别方法并不公开。上面的判断基于公开的研究和社区经验，不能保证今后不变。
- 流量大小、使用时段、IP 的历史记录这类特征与用什么脚本无关，任何方案都无法完全消除。

## 四、开工前需要核实的事项

与本文相关、仍依赖内核和客户端具体支持情况的有：

- 给 IP 申请正规证书是否可行。可行的话，无域名用户也能用受信任的证书，指纹固定只作后备。
- ECH 的服务端配置方式。
- Xray 的 Reality 抗量子签名选项在客户端的支持范围。
- XHTTP 上下行分离的客户端支持范围。

完整清单和已有结论的事项见[开发路线](09-开发路线.md)。
